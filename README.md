> 경매·공매 물건과 실거래가를 지도에서 함께 살펴보는 부동산 정보 탐색 서비스

**524만 건의 실거래 · 직접 구현한 데이터 배치 · 감정평가서 기반 RAG 상담**

흩어진 공공 데이터를 수집하고, 위치 → 물건 상세 → 같은 단지의 거래 내역으로 이어지는 탐색 흐름을 만들었습니다.

## 서비스 소개

경매 물건의 가격을 이해하려면 입찰 정보뿐 아니라 주변 거래와 건물 정보를 함께 확인해야 합니다. Rising Home은 법원 경매·온비드 공매와 실거래 데이터를 지도와 상세 패널로 연결합니다. 관심 물건을 저장하고 다시 찾아보는 흐름도 제공합니다.

## 주요 기능

### 지도에서 경매·공매 탐색

지역과 조건을 바꾸며 물건을 탐색하고, 단지를 선택해 경매·공매 목록과 상세 정보를 확인합니다. 상세에서는 가격, 일정, 사진과 문서를 살펴볼 수 있습니다.

### 실거래가 조회와 비교

매매·전월세, 주택 유형, 가격·면적 조건으로 거래를 조회합니다. 단지 상세와 면적별 거래 내역을 통해 물건의 가격을 비교할 수 있습니다.

### 감정평가서를 근거로 묻는 AI 상담

선택한 경매·공매 물건의 감정평가서에서 질문과 관련된 내용을 찾아 물건 상세와 함께 답변합니다. PDF 전체를 매번 전달하는 방식 대신, 문서의 장·절과 페이지 정보를 유지한 청크를 검색합니다. 검색 범위는 해당 물건과 감정평가서로 제한합니다.

### 관심 목록과 서비스 운영

관심 거래·경매를 저장하고 마이페이지에서 관리합니다. 공지, 뉴스, 문의·관리자 기능과 감정평가서 기반 AI 상담도 팀에서 구현했습니다.

### 감정평가서 RAG의 처리 흐름

| 단계 | 구현 내용 | 설계상 의미 |
| --- | --- | --- |
| 문서 선택 | 선택한 법원 경매·온비드 물건의 감정평가서 조회 | 다른 물건의 근거가 섞이지 않도록 시작점 고정 |
| 필요 시 색인 | 문서 ID·원문 URL로 색인 여부를 확인하고 최초 질문 때 처리 | 사용하지 않는 문서까지 미리 처리하는 범위 축소 |
| 문맥 보존 | 장·절 제목, 페이지·청크 순서와 일부 겹침을 유지 | 검색된 본문이 어느 항목의 내용인지 함께 전달 |
| 검색·답변 | 물건·출처·문서 유형 필터로 검색 후 상세 정보와 결합 | 일반 지식만으로 물건 설명을 생성하는 범위 제한 |

검색 근거가 부족할 때 단정하지 않도록 지시하지만, 프롬프트만으로 사실성을 보장하지는 않습니다. 텍스트가 추출되지 않는 문서는 오류로 처리하며, 최초 색인의 지연과 동시 요청·재색인 정책, 답변 정확도 평가는 후속 과제입니다.

## 직접 구현한 데이터 배치

지도와 상세 화면에 필요한 데이터를 직접 수집·정제·적재하는 **Spring Batch 애플리케이션**을 구현했습니다. 아파트·연립다세대의 매매·전월세 네 종류 원천을 지역·월 단위로 순회하고, API의 전체 건수를 기준으로 마지막 페이지까지 읽어 공통 거래 모델에 저장합니다.

| 단계 | 직접 구현한 처리 |
| --- | --- |
| 사전 검증 | 지역·기간·필수 API 설정을 검증한 뒤 수집 시작 |
| 거래 수집 | 시군구 × 월 × 거래 API별 페이지 순회, 원천 필드 정규화 |
| 범위 갱신 | 선택한 지역·기간의 거래만 교체하고 다른 지역의 기존 데이터 유지 |
| 조회 데이터 생성 | 단지·면적 타입 연결, 거래 기반 가격 스냅샷 갱신 |
| 위치·건축 보강 | 검증된 주소 좌표, PNU와 건축물대장 정보를 별도 작업으로 연결 |
| 일일 갱신 | 최근 3개월 거래와 파생 데이터만 갱신하고 외부 좌표·건축 API 재조회 분리 |

초기 수집은 전국 시군구와 2021년 6월~2026년 6월을 지정할 수 있도록 구성했습니다. **수집 대상으로 지정한 기간과 실제 DB에 남아 있는 기간·건수는 구분**합니다.

### 중단 이후 다시 처리할 범위를 남기기

온비드는 목록·상세·유찰 이력을 단계로 나누고 물건별 상세·입찰결과 완료 체크포인트를 저장합니다. 재실행 시 완료한 호출을 건너뛰어 남은 대상을 처리합니다. 건축HUB는 이미 보강한 필지를 제외하고, 일일 할당량 초과 응답에서 중단하도록 구성했습니다. 총괄표제부 응답이 없는 필지도 조회 완료로 기록해 동일한 빈 결과를 반복 요청하지 않게 했습니다.

동별 표제부는 법정동별로 페이지를 순회한 뒤 응답의 행정코드·지번에서 PNU를 재구성하여 같은 필지에 연결합니다. 단지마다 같은 법정동을 다시 요청하는 범위를 줄이고, 이미 적재된 단지·필지는 다음 실행에서 건너뜁니다. 다만 동별 표제부의 빈 응답은 별도 완료 표시가 없어 재조회될 수 있습니다.

실제 실행 기록에는 2026년 6월 24일 온비드 목록 1,589건 적재와 유찰 이력 처리 6,587건이 남아 있습니다. 이는 **각 단계의 실행 처리량**이며 현재 DB 누적 건수나 중복 제거 후 전체 물건 수로 해석하지 않습니다.

## 단지 통합과 전처리

실거래 원천은 거래 한 건이 한 행이므로, 지도에서 단지를 누르면 매매·전세·월세와 면적별 이력이 한곳에 모이도록 거래와 단지의 관계를 다시 구성했습니다.

### 이름보다 원천 식별자·지역·지번을 우선

아파트는 원천의 아파트 일련번호를 단지 식별자로 사용합니다. 이름이 같다는 이유로 서로 다른 지역의 단지를 합치지 않고, 동일 일련번호에 속한 거래를 하나의 단지로 연결합니다.

연립다세대는 법정동코드와 지번으로 묶고, 코드가 부족하면 시군구·동 이름을, 지번이 없으면 건물명을 보조 기준으로 사용합니다. 건물명이 누락된 원천은 동·지번을 표시 이름으로 사용합니다. 이 방식은 주소가 같은 거래를 연결할 수 있지만, 원천 주소 누락이나 한 필지의 여러 건물까지 완벽하게 구분하는 것은 아닙니다.

단지명 문자열의 유니코드·대소문자·기호와 ‘아파트’ 표기 정규화는 별도의 이름 매칭 보조에 사용합니다. 모든 단지를 정규화된 이름 하나로 합치는 방식으로 사용하지 않습니다.

### 거래 모델과 지도 가격을 만들기

금액의 쉼표·단위 문자를 정리하고 면적은 소수 셋째 자리로 맞춥니다. 임대 거래는 월세 금액 유무로 전세·월세를 구분하며, 법정동 코드는 시군구·읍면동 코드를 조합합니다. 원천 값도 보관하여 정규화 결과를 추적할 수 있게 했습니다.

연결된 단지 안에서 전용면적별 타입을 만들고, 단지·면적·거래 유형별 최신 순서를 계산해 최신 매매가·보증금·월세와 평균 가격을 스냅샷으로 구성합니다. 지도 가격과 상세 거래 이력이 같은 단지·면적 기준을 공유하도록 한 것입니다.

단지 주소나 법정동이 바뀌면 이전 PNU·좌표를 무효화해 과거 위치를 계속 사용하지 않도록 했습니다. 지오코딩은 주소 결과가 하나이고 법정동코드가 일치할 때만 저장합니다. 거래 정제 → 단지 연결 → 위치 검증을 분리해 잘못된 주소가 곧바로 지도 마커가 되는 범위를 제한했습니다.

## 설계에서 고려한 점

### 지도 축척에 따라 조회 단위를 나누기

넓은 범위에서도 개별 단지를 모두 표시하면 마커가 겹치고 결과가 과도해집니다. 지도 조회를 개별 단지 마커와 행정구역 집계로 나누고, 마커 응답에는 상한 초과 여부를 함께 전달하도록 구현했습니다.

단순히 결과 일부만 반환하면 사용자는 그 범위의 물건이 전부라고 오해할 수 있습니다. 잘림 여부를 응답에 남겨 화면에서 추가 탐색을 안내할 수 있도록 했습니다. 테스트에는 역전된 경계값 거절, 좌표 범위 검사, 반환 상한과 행정구역 집계가 포함되어 있습니다. 실측 응답시간이나 부하 개선율은 별도로 제시하지 않습니다.

### 데이터 갱신의 범위를 제한하기

지역·기간별 거래를 다시 수집할 때 다른 지역의 단지·좌표·건축 정보를 함께 지우지 않도록 처리 범위를 나눴습니다. 거래는 선택 범위를 교체하고, 파생 단지와 보강 정보는 갱신·추가하는 방식입니다. 이미 얻은 좌표·건축 정보를 매일 다시 조회하는 비용도 피하도록 갱신 작업을 구분했습니다.

## 결과와 한계

데이터 수집부터 지도 탐색, 상세 비교, 관심 목록까지 이어지는 서비스를 구현했습니다. 다만 수집 시점과 원천 기관의 갱신 주기에 따라 정보 차이가 생길 수 있으며, 좌표가 검증되지 않은 단지는 지도 노출에 제약이 있습니다. AI 상담과 조회 정보가 실제 권리 분석이나 입찰 판단을 대신하는 것은 서비스 범위에 포함하지 않습니다.
